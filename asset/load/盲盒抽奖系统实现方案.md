# 盲盒抽奖系统实现方案

## 一、方案概述

基于现有陪玩/代练平台（Spring Boot + MyBatis Plus + 微信支付），实现四级盲盒（5.9/15.9/30.9/59.9元）抽奖系统，包含**精确库存控制 + 多层级奖池 + 独立权益卡系统 + 现有订单支付流程**。

### 核心决策（基于用户确认）

* **支付流程**：盲盒购买走现有 `UnifiedOrderController` / `PayServiceImpl` / `WxPayNotifyController` 统一支付回调

* **权益卡管理**：新建独立 `user_benefit_card` 表，不混用现有 `sys_coupon/user_coupon`

* **抽奖算法**：精确库存原子扣减 + 多层级奖池（基础卡/永久卡/隐藏卡）权重随机

### 3.2 核心业务流程

#### 3.2.1 盲盒购买流程（复用现有支付）

```
用户选盲盒档位 + 抽奖次数(1/5/10)
    ↓
POST /blind-box/order/create
    ↓
生成 BlindBoxOrder（order_no=BBX...，status=0待支付）
    ↓
POST /pay/blindBox（新增盲盒支付类型）
    ↓
PayServiceImpl.doPayBlindBox()
    ↓
调起微信支付 JSAPI
    ↓
用户支付成功
    ↓
微信回调 → WxPayNotifyController → PayServiceImpl.handlePayNotify()
    ↓
识别 BBX 前缀 → handleBlindBoxNotify()
    ↓
更新 blind_box_order.pay_status=1, order_status=1已支付待抽奖
    ↓
（如使用优惠券，confirmUseCouponByOrderId）
```

#### 3.2.2 盲盒抽奖流程（精确库存 + 多层级奖池）

```
用户点击"立即抽奖"
    ↓
POST /blind-box/draw
    ↓
校验：订单已支付、未抽完、次数足够
    ↓
【多层级奖池选择】
    根据 activity 配置，先确定进入哪个奖池层级
    （默认：基础卡池概率70%，永久卡池概率25%，隐藏卡池概率5%）
    或固定比例：如 5.9元盲盒 → 基础卡池100%（16个奖品）
              → 永久卡池100%（9个奖品）
    实际按每个 prize 的 probability_weight 做加权随机
    ↓
【库存原子扣减】
    1. 查询该 activity + pool_type 下所有 status=1 且 stock>0 的奖品
    2. 过滤每日限量（检查 blind_box_prize_daily.draw_count < daily_limit）
    3. 计算剩余可用奖品的权重和
    4. 加权随机选中一个 prize
    5. 原子扣减库存：UPDATE blind_box_prize SET total_stock = total_stock - 1 WHERE id = ? AND total_stock > 0
       如 affectedRows=0，说明库存刚被扣完，回到步骤1重试（最多3次）
    6. 记录/更新 blind_box_prize_daily（INSERT ON DUPLICATE KEY UPDATE）
    ↓
【奖品发放】
    1. 插入 blind_box_record（status=1已发放）
    2. 插入 user_benefit_card（根据 prize_type 和 card_config_json 构造）
    3. 更新 blind_box_order.draw_count_remaining（或判断 order_status=2已抽完）
    ↓
返回抽奖结果
```

#### 3.2.3 权益卡使用流程（以陪玩订单为例）

```
用户创建陪玩订单 / 代练订单
    ↓
UnifiedOrderController.createOrder
    ↓
用户选择可用的权益卡（如：折扣卡、免排队卡）
    ↓
BenefitCardService.useCard(cardId, orderId, orderType)
    ↓
校验：卡是否有效、未过期、未超限、使用条件满足（如满40元）
    ↓
计算优惠后金额
    ↓
锁定权益卡：status=3已冻结，use_order_id=orderId
    ↓
用户支付
    ↓
支付回调确认 → BenefitCardService.confirmUseCard(orderId)
    ↓
卡状态更新：status=1已使用，used_uses+1
    ↓
如卡有剩余次数（total_uses > used_uses），status=0未使用，释放继续用
```

## 五、方案 C：高并发优化方案（Redis + Lua 预扣库存）

### 5.1 与方案 A 的差异

| 维度   | 方案 A（主方案）                              | 方案 C（高并发）                 |
| ---- | -------------------------------------- | ------------------------- |
| 库存扣减 | MySQL 行锁 `UPDATE ... WHERE stock > 0`  | Redis 预扣 + Lua 原子脚本       |
| 奖池加载 | 每次抽奖查 MySQL                            | 启动时加载到 Redis Hash，定时同步    |
| 每日限量 | MySQL `INSERT ON DUPLICATE KEY UPDATE` | Redis `INCR` + 过期时间（次日零点） |
| 抽奖性能 | \~50-100 TPS（MySQL 行锁）                 | \~1000+ TPS（Redis 内存操作）   |
| 复杂度  | 中等                                     | 较高（需处理 Redis 与 MySQL 不一致） |
| 适用场景 | 日常业务（预估日活 < 1万）                        | 大促/活动爆发（高并发抽奖）            |

### 5.2 高并发核心设计

```
启动时：BlindBoxPrizeLoader 加载所有奖品库存到 Redis
  - Redis Key: `blindbox:stock:{prizeId}` → String (剩余库存)
  - Redis Key: `blindbox:daily:{prizeId}:{yyyyMMdd}` → String (当日已抽)
  - Redis Key: `blindbox:pool:{activityId}:{poolType}` → ZSet (奖品ID + 权重)

抽奖时：
  1. Lua 脚本原子操作：
     - 检查 daily_limit（如存在）
     - 检查 total_stock（如存在）
     - 加权随机（在 Lua 中加载 ZSet）
     - 扣减库存、增加日计数
  2. Lua 返回选中 prizeId
  3. 异步写 MySQL（blind_box_record + user_benefit_card）
  4. 定时任务（每5分钟）将 Redis 库存同步回 MySQL
```

### 7.1 加权随机算法（Java）

```java
// 在 BlindBoxServiceImpl 中
private BlindBoxPrize weightedRandom(List<BlindBoxPrize> prizes) {
    int totalWeight = prizes.stream().mapToInt(BlindBoxPrize::getProbabilityWeight).sum();
    int random = ThreadLocalRandom.current().nextInt(totalWeight);
    int current = 0;
    for (BlindBoxPrize prize : prizes) {
        current += prize.getProbabilityWeight();
        if (random < current) {
            return prize;
        }
    }
    return prizes.get(prizes.size() - 1);
}
```

## 九、风险点与应对

| 风险         | 应对方案                                        |
| ---------- | ------------------------------------------- |
| 并发抽奖超卖     | 使用 `UPDATE ... WHERE stock > 0` 原子扣减，失败重试3次 |
| 支付回调重复通知   | 幂等检查 `pay_status == 1` 直接跳过                 |
| 权益卡发放失败    | 抽奖记录 `status=2发放失败`，后台管理可手动补发               |
| 奖池配置错误概率总和 | 后台管理界面校验权重，不要求总和为100，只要求相对权重合理              |
| 盲盒订单退款     | 如已抽奖则不可退款；未抽奖可原路退款（复用现有 refund 接口）          |
| 每日限量跨天     | 使用 `draw_date` 精确到天，凌晨3点定时任务清理计数            |

## 十、实施建议与优先级

### Phase 1（MVP，约 3-5 天）

1. 建表（`blind_box_activity`, `blind_box_prize`, `blind_box_order`, `blind_box_record`）
2. 盲盒购买 + 支付回调（走 `BBX` 订单号）
3. 基础抽奖接口（单抽，无每日限量，无库存精确控制）
4. 抽奖记录查询

### Phase 2（权益卡体系，约 3-5 天）

1. 建 `user_benefit_card` 表
2. 奖品发放逻辑（抽中后写入 user\_benefit\_card）
3. 权益卡列表/详情查询
4. 常用卡类型实现：折扣卡、立减卡、免排队卡

### Phase 3（完善与优化，约 2-3 天）

1. 精确库存控制（原子扣减 + 每日限量）
2. 权益卡使用接入下单流程（陪玩/代练订单使用权益卡）
3. 5连抽/10连抽批量接口
4. 定时任务：过期卡清理、库存同步

### Phase 4（高并发，可选）

1. 如 QPS 需求高，迁移到方案 C（Redis + Lua）

## 十一、总结

* **推荐方案 A** 作为主方案，它兼顾了功能完整性（精确库存、独立权益卡、多层级奖池）和与现有系统的无缝集成（复用订单支付流程）。

* **方案 B** 适合快速 MVP 验证，但上线后需要大量重构才能支持库存控制。

* **方案 C** 是方案 A 的高并发扩展，当日常业务并发不足以成为瓶颈时，不建议过早引入 Redis 复杂度。

* 整个系统预估新增 **约 20+ 文件，修改 3-5 个现有文件**，按 Phase 递进实施，可边上线边完善。
